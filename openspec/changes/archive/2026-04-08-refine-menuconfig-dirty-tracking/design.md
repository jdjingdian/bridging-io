## 上下文

当前 `menuconfig` 的全局 dirty 语义主要依赖会话内累计出来的 `dirty_paths`。这种模型实现简单，但它记录的是“哪些字段曾经被提交过编辑”，不是“当前内存草稿是否仍然偏离基线配置”。结果是：

- 普通字段一旦被改动，就会留下 dirty path；
- 即使之后把字段改回原值，dirty path 也不会自动清除；
- 根页面标题 dirty 标记与 `Esc` 退出保存确认都会继续出现；
- target 编辑流已经使用“当前值 vs baseline”的比较语义，而普通配置字段仍然停留在“编辑历史”语义，两者不一致。

这次变更不涉及配置 schema、保存文件格式或 apply strategy，而是修正 `menuconfig` 自身对“未保存修改”的真相定义。约束是：现有 UI 中已经有字段级 dirty 概念、target 编辑会话基线、根页面 dirty 标题和退出确认流程，因此设计需要尽量复用这些结构，而不是引入第二套并行状态机。

## 目标 / 非目标

**目标：**

- 让 `menuconfig` 的全局 dirty 状态只反映“当前配置相对会话基线是否存在真实差异”。
- 让普通字段在值被改回基线后自动清除 dirty，而不是继续留下误导性的未保存状态。
- 统一普通配置字段与 target 编辑流的基线比较语义，减少不同页面之间的行为分裂。
- 保持现有 `Yes / No / Cancel` 退出确认链路、保存入口和配置写回语义不变，只修正触发条件。

**非目标：**

- 本次不改动 `config.toml` schema 或持久化格式。
- 本次不重新设计 `menuconfig` 的 footer、按钮区或保存确认弹窗文案。
- 本次不把 `menuconfig` 的 `s` 快捷键语义扩展为“智能 apply”或其他新流程。
- 本次不重做 target 创建/管理会话的整体状态机，只在需要处把它与根配置 dirty 语义对齐。

## 决策

### 决策 1：为 `MenuConfigApp` 引入正式的全局基线配置快照

根页面的 dirty 真相必须来自“当前 `settings` 与基线 `settings` 是否相等”，而不是来自某个增量记录列表。最直接、最稳妥的做法是在加载 `menuconfig` 时保存一份会话基线配置，并在每次成功保存后刷新这份基线。

选择这个方向，而不是继续依赖 `dirty_paths` 的原因是：

- `CoreSettings` 已经支持结构化 `PartialEq/Eq`，可以直接比较内存模型；
- 这能自然覆盖“字段改了又改回去”的场景，不需要为每个字段单独写撤销逻辑；
- 它与 target 编辑会话里已有的 baseline 比较心智一致。

不采用 “序列化为 TOML 后比较字符串” 的原因是：那会把格式化、字段顺序和默认值渲染差异误引入 dirty 语义；这次需要的是配置模型等价，而不是文本等价。

### 决策 2：`dirty_paths` 保留，但降级为“当前偏离基线字段集合”的派生状态

`dirty_paths` 仍然有价值，因为行级 UI、搜索结果或未来矩阵文档可能需要展示“哪些字段当前是 dirty 的”。但它不再适合作为全局 dirty 的真相源。

因此更合适的语义是：

- `is_dirty()` 基于 `settings != baseline_settings` 判断；
- `dirty_paths` 只表示“当前仍偏离基线的字段路径”；
- 字段提交后，如果该字段值与基线一致，则从 `dirty_paths` 中移除；否则加入；
- save 成功后清空 `dirty_paths` 并刷新 `baseline_settings`；
- target 删除、回滚或 apply 后，也要同步清理或重建对应路径，避免留下过期索引。

选择“保留并派生”而不是“完全删除 `dirty_paths`”的原因是：这样能减少 UI 层改动面，也便于后续继续做字段级 dirty 展示或测试断言。

### 决策 3：target 编辑流继续保留局部 baseline，但要与全局基线协调

target 编辑流已经有自己的 `TargetEditSession.baseline`，它表达的是“进入该 target 详情页时的局部基线”。这套机制仍然合理，因为 target 流程需要支持：

- 创建会话未提交时的整草稿丢弃；
- 管理会话未应用时回滚到进入详情页前的 target 基线；
- 详情页内 `Apply Target --->` 与根页面 `Save` 的语义分层。

本次不移除这套局部 baseline，但要求它与全局基线协调：

- target 局部“是否存在未提交编辑”继续用 target baseline 比较；
- 根页面“是否需要保存整个配置”用全局 baseline 比较；
- 当 target 会话执行 `Apply Target --->` 时，更新的是 target 局部 baseline，而不是全局保存基线；
- 只有执行 `Save` 后，新的整体 `settings` 才成为全局 baseline。

这样可以保留“Apply 只是提交当前 target 编辑会话，Save 才是配置文件落盘”的现有心智，同时消除普通字段与 target 字段在 dirty 判定上的不一致。

### 决策 4：退出确认只对真实未保存差异负责

根页面 `Esc` / `Exit` 的保存确认弹窗必须只在“当前整体配置仍偏离全局基线”时触发。也就是说：

- 若字段经历 `info -> debug -> info` 这类回退，根页面不再显示 dirty，也不再弹保存确认；
- 若 target 会话内已经 `Apply`，但尚未 `Save` 到磁盘，只要整体配置仍不同于全局基线，根页面仍然必须提示保存；
- 若 target 会话放弃修改并回滚到局部 baseline，且整体配置也未偏离全局基线，则退出时直接离开。

不采用“只要发生过编辑就提示一次保存”的原因是：这会把“会话历史”误传达成“当前仍有未保存配置”，与用户心智和当前产品文案都不一致。

## 风险 / 权衡

- [风险] target 删除或回滚会导致 `targets[i]` 索引变化，若继续手工维护路径列表，可能留下过期 dirty path
  → 缓解措施：对 target 相关路径优先采用基于当前状态重算或成组清理，而不是只做单向追加。

- [风险] 全局基线与 target 局部 baseline 并存，若职责边界不清，会让后续维护者误解哪个才是保存真相
  → 缓解措施：在设计与实现中明确区分“会话提交基线”和“磁盘保存基线”，并让 `is_dirty()` 只依赖全局基线。

- [风险] 如果把 dirty 计算改成每次都全量扫描所有字段，后续字段继续增多时可能增加维护成本
  → 缓解措施：全局 dirty 直接比较 `CoreSettings` 结构体；字段级 dirty 只在编辑提交、target 回滚、save 成功等边界事件更新。

- [风险] 现有测试大多把 `dirty_paths` 当成断言对象，调整后可能出现一批测试跟随语义变化而失败
  → 缓解措施：把测试重点转向“退出是否提示保存”“dirty 标题是否显示”“字段回退后是否消脏”，保留少量必要的路径级断言。

## 迁移计划

1. 在 `MenuConfigApp` 中引入全局 baseline 配置快照，并把 `is_dirty()` 切换到结构化比较。
2. 调整普通字段编辑、布尔/choice 提交、target 删除/回滚/apply/save 等路径，对 `dirty_paths` 执行基于基线的增删或重算。
3. 补充回归测试，覆盖字段改回原值、target 改回原值、apply 后未 save、discard 回滚与 save 后基线刷新。
4. 更新相关 spec 和 matrix 文档，明确 dirty/退出确认的正式语义。

## 未决问题

- `dirty_paths` 是否要继续严格保持“字段级最小集合”，还是允许 target 相关路径在个别边界上采用更粗粒度重算；当前倾向于后者，只要 UI 与测试语义稳定即可。
- 当用户在“无真实差异”的状态下主动按 `s` 保存时，是否需要显式提示“无变更可保存”；本次可暂不改变该交互，后续若需要可独立设计。
