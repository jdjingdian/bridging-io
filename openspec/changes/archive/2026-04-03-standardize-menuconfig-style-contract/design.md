## 上下文

当前仓库已经有一批与 `menuconfig` 相关的正式能力：

- `standalone-operator-console` 已定义树形导航、`Esc` 返回/退出、dirty tracking、`--->` 导航样式和基础行语法；
- `menuconfig-selection-contrast` 已定义主菜单与底部按钮需要共享反色高亮与 fallback 样式；
- 代码实现已经具备整体居中、文本左对齐、底部按钮栏、文本输入光标和若干 popup。

但这些信息仍然不足以形成完整的 menuconfig 风格合同，主要缺口在于：

1. 行语法虽有雏形，但“固定关闭/固定开启/只读说明/可切换/可进入”的完整语法还没有正式归一。
2. 焦点规则仍然不完整。当前实现会把 `Info` 行当成禁用态渲染，但导航仍可能停在它上面，这与“不可更改项必须直接跳过”的目标冲突。
3. 反色高亮目前主要覆盖菜单区和底部按钮区，确认弹窗与单选弹窗尚未正式纳入统一选中态语义。
4. 文本输入、选择弹窗、帮助弹窗、一次性 reveal、确认弹窗虽然都存在，但没有一份统一的 popup style contract。
5. 最小终端尺寸保护、行溢出裁剪和“搜索结果/空状态是否复用同一语法”尚未被正式定义。
6. 缺少一份专门的 style matrix。未来新增 `menuconfig` 功能时，团队很难快速核对“这一行该用什么前缀、是否可聚焦、空格/回车/ESC 如何解释”。

本次 change 的目标不是立刻实现所有代码，而是先把“menuconfig 长什么样、怎么选、哪些行能聚焦、弹窗如何表现、哪些偏差必须修复”完整沉淀成正式合同，并为后续实现提供唯一真相源。

## 目标 / 非目标

**目标：**

- 为 `menuconfig` 定义完整、可执行的风格合同，覆盖布局、行语法、焦点规则、选中态、弹窗和文本输入。
- 建立一份 canonical 的 `MENUCONFIG_STYLE_MATRIX`，使后续功能开发必须对照该矩阵落地。
- 把当前已知风格偏差明确记录为本 change 的 must-fix 范围，并阻止“带着风格已知问题直接归档”。
- 保持整体风格对齐 Linux kernel `menuconfig` / OpenWrt `menuconfig` 的阅读节奏：单栏、逐级进入、前缀突出、左读清晰。

**非目标：**

- 本轮不编写或修改应用代码实现。
- 不改变现有 Security、Token Management、Vault 等业务能力的功能边界。
- 不引入主题系统、自由换肤能力或多套并存风格。
- 不把 `menuconfig` 改造成分栏 dashboard 或持久侧边栏式 UI。

## 决策

### 决策 1：`menuconfig` 采用固定的单栏布局和前缀语法

方案：

- 所有主页面保持单栏菜单列表，不分栏，不在主流程中引入常驻侧面板。
- 菜单列表整体在屏幕中居中，但文本列保持左对齐。
- 每一行使用固定宽度的“焦点标识列 + 语义前缀列 + 文本列 + 可选后缀列”。
- 行语法固定为：
  - `---`：只读描述/状态信息
  - `- -`：当前不可更改、固定关闭的功能
  - `-*-`：当前不可更改、固定开启的功能
  - `< >` / `<*>`：单选或唯一启用语义入口
  - `[ ]` / `[*]`：多选项
  - `--->`：进入下一级页面、编辑弹窗、确认流程或结果弹窗
  - `>`：当前选中项最左侧焦点标识

原因：

- 让操作者不依赖帮助文本，只看一行就能判断“能不能选、按空格还是回车、会不会进入下一层”。
- 固定语法也让搜索结果、详情页、占位页与主菜单可以共享同一种阅读方式。

备选：

- 继续使用“由各页面自行决定”的弱约定。该方案会继续导致风格漂移。
- 采用多列/卡片化布局。该方案与 Linux kernel `menuconfig` 的目标不一致。

### 决策 2：不可更改项必须不可聚焦，并在导航时直接跳过

方案：

- `---`、`- -`、`-*-` 统一视为 non-focusable row。
- 初次进入页面、页面刷新、搜索结果变化或状态变化后，焦点必须自动落在最近的可聚焦项。
- `↑/↓` 循环导航必须只在可聚焦项之间闭环，直接跳过 non-focusable row。

原因：

- “灰掉但还能停住焦点”会让用户误以为这是一项可执行操作，只是暂时不可用。
- 你的要求非常明确：不可更改类型在菜单中无法被选中，上下移动遇到时应顺延跳过。

备选：

- 允许禁用项获得焦点，但不反色。该方案仍然破坏“能聚焦即能操作”的心智。

### 决策 3：所有可操作焦点体共享同一选中态语义

方案：

- 主菜单选中行、底部按钮焦点、确认弹窗按钮、单选列表当前项都必须共享同一反色高亮策略。
- 当终端不支持反色时，所有这些焦点体都必须切到同一 fallback 语义，而不是只给部分区域降级。
- 只读弹窗或没有可操作项的结果弹窗不要求强制显示选中态。

原因：

- 当前已有的高亮规范只覆盖菜单与 footer，不足以覆盖 popup。用户在确认或选择弹窗中同样需要快速定位焦点。

备选：

- 对 popup 继续只用尖括号或星号提示。该方案不够强，也与主菜单形成断裂。

### 决策 4：`Space` 与 `Enter` 语义必须由行前缀和后缀共同决定

方案：

- `[ ]` / `[*]`：`Space` 切换，`Enter` 不应隐式切换。
- `< >` / `<*>` 且带 `--->`：`Space` 切换启用状态，`Enter` 进入下一层。
- 文本字段或枚举字段：显示为 `Label (value) --->`，`Enter` 进入编辑弹窗，`Space` 仅在明确要求时等价于进入选择流程。
- 纯流程入口或管理动作：统一使用 `--->`，由 `Enter` 进入。
- 为避免歧义，禁止把 `[ ]/[*]` 与 `--->` 混用；若某项既需要切换又需要进入下一级，必须使用 `< >/<*> + --->` 的单选入口语法。

原因：

- `Space`/`Enter` 的稳定分工是 menuconfig 体验的一部分，也是避免误操作的关键。

### 决策 5：所有 popup 都必须服从统一的 overlay contract

方案：

- 确认、单选、文本输入、帮助、一次性结果、最小视口保护都采用 centered overlay。
- popup 打开后，背景菜单冻结，不接受穿透导航。
- `Esc` 优先关闭当前 popup，而不是把事件穿透给底层菜单。
- 文本输入 popup 必须显示真实光标，并支持 `Left/Right` 移动、`Backspace` 删除左侧字符、`Enter` 提交、`Esc` 取消。

原因：

- 当前 popup 存在，但没有统一的交互合同。把这些流程统一收束后，后续新增字段编辑或确认链路才不会各写一套。

### 决策 6：建立正式的最小视口和溢出裁剪规则

方案：

- 采用 `80x24` 作为 `menuconfig` 的最低支持视口。
- 当终端小于该尺寸时，系统必须展示 resize-required overlay，而不是继续渲染错位或截断后不可判读的主界面。
- 菜单行禁止自动换行；溢出时必须优先保留左侧焦点标识、语义前缀和右侧 `--->`，中间文本可使用 `...` 截断。
- 状态栏与帮助/说明内容可以换行，但主列表行不得折成多行。

原因：

- 这是避免“布局仍能渲染，但风格语义已经被挤坏”的最低保护。

### 决策 7：建立 canonical 的 style matrix，并要求当前偏差在本 change 内修复

方案：

- 新增 `docs/matrix/MENUCONFIG_STYLE_MATRIX.md` 作为风格真相源。
- 矩阵必须覆盖布局区域、行类型、前缀/后缀、可聚焦性、键位语义、popup 样式、fallback、视口与溢出规则。
- 矩阵必须带有 `Known Current Deviations` 段落，用于记录当前实现与合同不一致的地方。
- 本 change 在归档前，必须清空该段落中属于本轮定义范围的已知偏差。

原因：

- 仅有 prose spec 不足以支持未来增量开发；matrix 能让团队快速核对新增页面或新增行是否破坏标准。

## 当前已知偏差（本 change must-fix）

1. 不可更改的 `Info` 行仍可能获得焦点，且会显示左侧 `>`，与“不可选且自动跳过”冲突。
2. 确认弹窗与单选弹窗没有与主菜单共享一致的反色/降级高亮语义。
3. 最小视口保护与菜单行溢出裁剪规则尚未统一实现。
4. 搜索结果、空状态、锁定提示等特殊页面需要统一审计，确保继续复用同一行语法与焦点规则。

## 风险 / 权衡

- [风险] 风格合同写得更严格后，当前实现会暴露更多不合规点。
  -> 缓解：把这些点显式纳入本 change 的 must-fix 列表，而不是继续口头接受。

- [风险] style matrix 增加文档维护成本。
  -> 缓解：矩阵只维护真正稳定的交互语法，不记录实现细节；新增 menuconfig 页面时只需映射到既有类型。

- [权衡] 固定语法减少了页面自由度，但换来一致、可学习、可测试的 operator experience。

## 迁移计划

1. 新建独立的 style-contract change，完成 proposal / design / tasks / spec delta。
2. 新增 canonical 的 `MENUCONFIG_STYLE_MATRIX`，并把当前偏差登记为 must-fix。
3. 后续实现阶段按矩阵修复 `bridgingio-operator-console` 的风格偏差。
4. 为焦点跳过、popup 高亮、最小视口和溢出裁剪补充测试。
5. 在已知偏差清空前，不归档本 change。

## 开放问题

- fallback 文本是否统一使用当前已有的 `>>` 风格，还是后续需要扩展为更强的无障碍变体；当前建议先继续复用 `>>`。
- 最小视口保护出现时，是否允许在 popup 内直接提示“按 Esc 退出”；当前建议允许。
