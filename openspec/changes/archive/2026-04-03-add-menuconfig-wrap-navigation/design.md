## 上下文

当前 menuconfig 的垂直导航在列表边界采用“夹住(clamp)”策略：当焦点位于第一项时按 `↑` 不再移动，位于最后一项时按 `↓` 不再移动。该行为在长列表中会增加反向多次按键成本，且不符合很多终端菜单对“循环滚动”的操作预期。

本次变更仅涉及 menuconfig 列表焦点移动规则，不引入新数据模型、不改变配置语义与持久化结构。

## 目标 / 非目标

**目标：**
- 将 menuconfig 列表的 `↑/↓` 导航改为首尾循环。
- 保证该规则在主菜单与子菜单等列表场景下行为一致。
- 补充可回归验证的边界测试，覆盖首项、末项、单项和空列表。

**非目标：**
- 不改变 `Enter`、`Esc`、`←/→` 的既有语义。
- 不调整菜单项渲染样式、主题与布局。
- 不引入新的键位映射配置能力。

## 决策

### 决策 1：垂直导航从 clamp 改为 modulo 循环
- 方案：将焦点索引更新规则统一为基于列表长度的循环计算。
  - `↑`：`(index + len - 1) % len`
  - `↓`：`(index + 1) % len`
- 原因：逻辑简单、可预测，天然覆盖首尾互跳。
- 备选：
  - 保持 clamp 并增加额外快捷键（如 Home/End）作为补偿。该方案无法消除边界停滞，不满足目标。
  - 在边界发出提示音/提示文案。该方案仅提示问题，不改善操作效率。

### 决策 2：空列表与单项列表采用稳定无副作用行为
- 方案：
  - 空列表时忽略 `↑/↓`，保持状态不变且不报错。
  - 单项列表时 `↑/↓` 后仍停留在该项。
- 原因：避免 modulo 对 `len=0` 的非法计算，并确保边界输入安全。
- 备选：对空列表输入抛错或显示强提示，会引入不必要噪音并影响交互连贯性。

### 决策 3：将循环逻辑收敛到统一的焦点移动入口
- 方案：在现有列表焦点移动路径中集中处理 `↑/↓` 循环，避免在多个分支重复实现。
- 原因：减少后续维护成本，避免主菜单/子菜单行为漂移。
- 备选：在各页面各自实现导航更新，短期可行但长期易产生不一致。

## 风险 / 权衡

- [风险] 循环逻辑误作用到非列表区域（如底部按钮栏）导致交互回归。
  -> 缓解：仅在“菜单列表焦点上下移动”路径启用，不改变按钮栏左右焦点规则。

- [风险] 列表动态变化（过滤、刷新）与索引更新同时发生时可能出现越界。
  -> 缓解：在每次渲染前基于当前列表长度归一化索引，并补充相应用例。

- [权衡] 循环导航提升连续操作效率，但与少数“边界停住”习惯存在差异。
  -> 缓解：将行为写入帮助文案与规范，保证预期一致。

## 迁移计划

1. 更新列表焦点移动逻辑，替换边界 clamp 为循环计算。
2. 校验主菜单、子菜单、过滤结果列表等路径是否共用同一导航入口。
3. 增加/更新单元与交互测试：首项按 `↑`、末项按 `↓`、单项列表、空列表。
4. 回归验证通过后发布；如出现严重兼容问题，可回滚到旧索引计算实现。

## 开放问题

- 搜索结果列表与帮助面板中的可导航列表是否也应保持完全一致的循环规则（建议是）。
- 是否需要在状态栏短暂提示“循环到首/尾项”来帮助首次用户建立心智（当前建议不加，保持界面简洁）。
