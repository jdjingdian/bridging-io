## 上下文

现有 menuconfig 交互中，底部操作按钮（如 `[<Select>]`、`< Exit >`、`< Help >`）已经对焦点项使用反色显示，但菜单列表的当前选中项缺少同等级视觉反馈。用户在键盘导航（上下移动、确认）过程中，需要在按钮区与菜单区之间切换注意力，当前不一致的高亮策略会增加定位成本与误选概率。

本次变更属于终端交互表现层优化，不引入新的业务数据模型；但会影响渲染状态映射、终端能力降级路径和 UI 回归测试基线。

## 目标 / 非目标

**目标：**
- 为菜单列表选中项提供必须可见的反色反馈。
- 统一菜单区与按钮区的选中态视觉规则，减少交互认知切换。
- 在终端不支持反色时提供明确降级策略，保证可读性与可区分性。
- 输出可回归验证的行为约束（键盘导航、状态切换、终端兼容）。

**非目标：**
- 不调整 menuconfig 的键位绑定、信息架构或交互流程。
- 不重构整体主题系统或引入新的复杂配色体系。
- 不修改按钮文案、菜单数据来源或业务逻辑。

## 决策

### 决策 1：菜单选中态采用与按钮选中态一致的反色策略
- 方案：将菜单项 `selected` 状态映射到与按钮焦点态一致的反色样式 token。
- 原因：已有按钮区反色已被验证可读，直接复用可降低实现与认知成本。
- 备选：
  - 独立颜色高亮：需要额外主题维护，且在不同终端配色下可读性不稳定。
  - 仅添加符号前缀（如 `>`）：可见性弱于整行反色，不满足“更直观”的目标。

### 决策 2：定义状态优先级，避免样式冲突
- 方案：渲染前先判定语义状态，再映射样式；优先级为 `disabled` > `selected` > `normal`。
- 原因：禁用语义必须保持，不应因选中焦点而伪装为可执行项。
- 备选：`selected` 覆盖 `disabled`，会导致交互误导，放弃。

### 决策 3：反色不可用时采用明确降级而非静默失效
- 方案：当终端能力探测判定不支持反色时，菜单选中项必须切换到可见降级样式（例如前缀标记 + 强调文本），并与按钮区一致。
- 原因：静默回退会使选中态再次不可见，违背本次变更目标。
- 备选：无降级策略，直接使用普通文本，放弃。

## 风险 / 权衡

- [风险] 终端对反色能力支持不一致，可能出现“部分环境不生效”。
  -> 缓解：引入能力探测分支，并覆盖 fallback 回归用例。

- [风险] 选中态与禁用态、搜索命中态等已有样式冲突。
  -> 缓解：明确状态优先级并通过快照/渲染测试锁定。

- [权衡] 统一反色策略提升一致性，但会减少主题自定义空间。
  -> 缓解：后续可在不破坏规范的前提下扩展 token 映射。

## 迁移计划

1. 在渲染层新增菜单项 `selected` 的样式映射，并复用按钮反色 token。
2. 接入终端能力探测结果，对不支持反色环境启用 fallback 样式。
3. 补充回归测试：导航切换、状态优先级、fallback 行为。
4. 灰度验证后默认启用；若发生兼容性问题，可暂时切回 fallback-only 模式。

## 开放问题

- fallback 的具体表现形式（符号前缀、粗体、下划线）是否已有项目内统一约定。
- 是否需要对高对比度/无障碍模式额外提供可配置开关。
