## 新增需求

### 需求:menu 列表选中项必须使用反色高亮
menuconfig 在渲染菜单列表时，当前选中项必须使用反色样式显示，且未选中项禁止使用同等反色样式。

#### 场景:键盘导航切换选中项
- **当** 用户在 menu 列表中通过方向键把焦点从选项 A 移动到选项 B
- **那么** 选项 B 必须显示反色高亮，且选项 A 必须恢复为非反色样式

#### 场景:初始进入菜单
- **当** 用户首次进入一个包含可选项的 menu 页面
- **那么** 当前默认选中项必须立即以反色样式显示，禁止出现“无选中态可见反馈”

### 需求:菜单区与按钮区的选中态反馈必须一致
系统必须让 menu 列表与底部按钮区在“被选中/聚焦”时采用一致的视觉策略；当按钮区使用反色时，菜单区选中项也必须使用反色。

#### 场景:菜单区与按钮区切换焦点
- **当** 用户在同一页面中从 menu 列表切换到 `[<Select>]` / `< Exit >` / `< Help >` 按钮区，再切回 menu 列表
- **那么** 两个区域在各自选中态下都必须保持同一反色策略，禁止一个区域反色、另一区域无等价高亮

### 需求:终端不支持反色时必须提供可见降级样式
当运行环境不支持反色能力时，系统必须对 menu 选中项与按钮选中态同时启用可见降级样式，禁止静默回退为普通文本。

#### 场景:反色能力不可用
- **当** 终端能力探测结果为不支持反色
- **那么** 当前选中项必须以约定的降级样式显示，并与未选中项保持可明确区分

### 需求:选中态渲染不得破坏禁用态语义
系统必须保证禁用项语义优先于选中高亮语义；禁用项禁止因为获得焦点而显示为可执行项视觉状态。

#### 场景:焦点移动到禁用项
- **当** 用户导航到一个禁用菜单项
- **那么** 该项必须保持禁用语义样式，并且不得呈现与可执行选中项等价的高亮反馈
