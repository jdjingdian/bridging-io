## 上下文

当前 `bridgingio-core --self-test` 已覆盖 one-shot、interactive shell、runtime execute path 与 host platform contract snapshot，但没有验证默认 MCP model-plane 监听地址 `127.0.0.1:19718` 的可绑定性。与此同时，standalone/default MCP 入口的产品语义已经把 `127.0.0.1:19718` 视为默认地址，因此一旦该地址在操作员机器上不可绑定，现有 self-test 不能直接暴露问题。

这次变更的核心约束有三点：

- `--self-test` 仍然必须保持无配置执行，不要求额外 runtime root 或外部依赖。
- 失败输出必须能帮助定位问题，尤其是 Windows 上的 `bind` 错误，而不是只返回抽象的“启动失败”。
- 这次只增强诊断与 smoke coverage，不扩展成自动提权、端口自动回退或长期驻留 listener 的行为变更。

## 目标 / 非目标

**目标：**

- 让 `bridgingio-core --self-test` 显式探测默认 model-plane 地址 `127.0.0.1:19718` 的绑定能力。
- 让绑定失败时输出原始错误文本，并把该检查纳入 self-test 的非零退出码判定。
- 让 OpenSpec 与 contract 文档明确 self-test 已覆盖默认 MCP 监听地址的绑定诊断。

**非目标：**

- 不修改默认 model-plane host/port。
- 不在 self-test 中真正启动长期运行的 HTTP 服务或处理真实 MCP 请求。
- 不引入管理员提权、UAC 弹窗、自动换端口或其他恢复策略。

## 决策

### 决策 1：self-test 必须复用生产 model-plane 绑定路径做短暂探针

`--self-test` 的绑定检查应尽量走与正常启动一致的绑定代码路径，而不是单独手写一个“近似检查”。这样产生的成功/失败语义才最接近真实 standalone 启动行为，错误信息也更容易和正式启动日志对齐。

考虑过的替代方案：

- 直接在 self-test 里写独立的 `TcpListener::bind(127.0.0.1:19718)` 探针。
  - 优点：实现简单。
  - 放弃原因：容易与正式启动路径漂移，后续如果 model-plane 绑定前置校验变化，自检可能失真。
- 继续只校验 `port = 0` 或随机端口。
  - 优点：更稳定，不易受环境占用影响。
  - 放弃原因：无法回答“默认产品入口 19718 在当前机器上能否工作”这个核心诊断问题。

### 决策 2：绑定检查只做短暂获取与立即释放，不承载 HTTP 流量

self-test 应只验证“默认地址是否可绑定”，不需要在该端口上继续接收请求。探针成功后应立即释放监听句柄，再继续后续自检步骤，避免把 self-test 变成一个依赖额外清理时序的长生命周期服务。

考虑过的替代方案：

- 成功绑定后继续发一个 `/health` 或 `/mcp` 请求验证。
  - 优点：覆盖更完整。
  - 放弃原因：会把这次变更从“绑定诊断”扩大成完整 HTTP smoke，超出当前问题范围，也会增加 self-test 的复杂度。

### 决策 3：失败输出必须打印 host/port 与底层错误原文

自检失败信息必须至少包含目标地址 `127.0.0.1:19718` 与底层错误文本，避免只留下通用失败摘要。这样操作员才能区分端口占用、保留端口、权限类拒绝或其他 I/O 错误。

考虑过的替代方案：

- 只打印“default model-plane bind failed”。
  - 放弃原因：诊断价值不足，无法支持 Windows 现场排查。
- 对错误做过度归类并隐藏原始文本。
  - 放弃原因：初期很容易误分类型，原始错误仍然是最可靠的排障依据。

## 风险 / 权衡

- 环境占用导致自检失败是预期行为，不是测试噪音
  → 这项检查的目标正是发现默认产品入口不可用，因此端口占用应当保留为失败。
- 复用正式绑定路径可能使 self-test 对未来 model-plane 初始化改动更敏感
  → 这是有意接受的耦合；self-test 的价值就在于贴近真实启动路径。
- 打印底层错误可能暴露平台差异化文案
  → 这是诊断所需信息，文档与测试断言应尽量匹配“包含错误文本”而不是完全匹配平台特定字符串。
