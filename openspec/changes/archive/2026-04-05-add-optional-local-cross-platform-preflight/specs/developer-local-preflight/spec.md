## 新增需求

### 需求:开发者本地跨端预检必须保持可选且非正式门控
项目必须提供一个可选的本地 cross-platform preflight 入口，用于帮助开发者在研发阶段提前发现跨平台编译或环境问题。该入口必须允许在未配置远端宿主时受控跳过，禁止把“未配置本地 preflight”视为正式失败或合并阻塞条件。

#### 场景:开发者未提供本地 preflight 配置
- **当** 开发者执行本地 preflight 入口，但当前机器上不存在约定的本地配置文件，也未显式传入配置路径
- **那么** 系统必须返回明确的 skipped / not-configured 结果，并提示如何提供本地配置，而不是把该情况视为脚本失败

#### 场景:仅使用正式 CI 的贡献者不受影响
- **当** 某个贡献者未配置任何本地 cross-platform preflight 宿主
- **那么** 项目必须仍允许其继续使用现有的本地 `cargo` / 正式 CI 工作流，而不是要求先配置远端宿主才能开发

### 需求:本地 preflight 配置必须与仓库跟踪内容隔离
本地 preflight 的真实宿主信息必须保存在 gitignored 配置中，仓库内仅允许跟踪示例配置文件与说明文档。示例配置禁止包含真实 IP、端口、用户名、私钥路径或其他个人环境细节，且示例文件本身不得被自动视为有效运行配置。

#### 场景:仓库提供示例配置
- **当** 项目为本地 preflight 提供示例配置文件
- **那么** 该示例文件必须只展示字段结构与默认语义，而禁止包含可直接连接真实宿主的个人环境数据
- **并且** 该示例文件必须作为仓库内可发现的 example 模板提供给开发者复制与本地化

#### 场景:示例配置不会意外触发远端运行
- **当** 开发者尚未创建自己的 gitignored 本地配置，只存在仓库跟踪的示例配置
- **那么** 本地 preflight 入口必须不把示例文件当作激活配置，而是继续返回 not-configured 或要求显式复制/指定本地配置

### 需求:远端验证必须基于当前工作树快照执行
本地 preflight 必须打包开发者当前工作树的快照并传输到远端宿主执行验证，而不是要求远端预先 clone 仓库、checkout 指定分支或仅验证已提交状态。打包过程必须排除明显的临时目录与构建产物目录，避免不必要的传输噪声。

#### 场景:未提交改动进入远端验证
- **当** 开发者在本地存在尚未提交的工作树改动并执行 preflight
- **那么** 系统必须将这些当前改动包含在发送到远端的快照中，使远端验证针对“当前正在编辑的代码”而不是远端旧副本

#### 场景:远端宿主无需维护仓库 clone
- **当** 开发者首次在某个远端 Linux 或 Windows 宿主上运行本地 preflight
- **那么** 系统必须能够通过上传并解包当前工作树完成验证，而不是要求该宿主先自行 clone 仓库或配置 git 凭据

### 需求:Windows 远端必须默认使用 PowerShell 或 cmd，Git Bash 只能作为可选附加能力
Windows 远端参与本地 preflight 时，系统必须默认通过 PowerShell 或 cmd 执行编译优先的验证路径，不得把 Git Bash 作为必需前置条件。只有在系统检测到 Git Bash 可用且本地配置显式启用附加检查时，才可以追加 bash 相关测试。

#### 场景:Windows 宿主未安装 Git Bash
- **当** 开发者对仅具备 OpenSSH、Rust 与 Windows 默认 shell 的宿主执行 preflight
- **那么** 系统必须仍能完成默认的 Windows compile-first 验证，而不是因为缺少 Git Bash 直接拒绝该宿主

#### 场景:检测到 Git Bash 且显式启用附加检查
- **当** Windows 宿主可用 Git Bash，且开发者在本地配置中显式启用了 bash 附加验证
- **那么** 系统必须先完成默认的 Windows 验证，再在受控的附加步骤中运行 bash 相关检查，而不是把 Bash 检查混成所有 Windows 运行的强制路径

### 需求:默认运行模式必须优先暴露跨平台编译问题
本地 preflight 的默认模式必须是 compile-first，并至少覆盖测试相关代码的编译与链接路径。系统必须允许后续扩展到更深的验证模式，但默认模式不得一开始就要求完整的远端集成测试或正式 contract gate。

#### 场景:执行默认 compile-only 模式
- **当** 开发者未显式覆盖运行模式并启动 preflight
- **那么** 系统必须以 `cargo test --workspace --no-run` 或等价的 compile-first 命令作为默认远端验证路径，以尽早暴露跨平台编译或链接问题

#### 场景:`cargo build` 通过但测试目标编译失败时仍应失败
- **当** 某个平台上 `cargo build --workspace` 可以通过，但 `cargo test --workspace --no-run` 在测试目标编译阶段失败
- **那么** 本地 preflight 必须将该平台结果判定为失败并保留失败摘要，而不是把这类问题误判为通过

#### 场景:显式选择更深验证模式
- **当** 开发者显式选择更深的本地 preflight 模式，例如单元测试或扩展检查
- **那么** 系统必须在默认 compile-first 语义之上追加这些检查，而不是改变“默认优先发现编译问题”的基线

### 需求:本地 preflight 结果必须保留在忽略目录中供研发回看
每次本地 preflight 运行后，系统必须在 gitignored 的本地目录中保留简洁的运行摘要与关键日志，至少包含目标宿主、运行模式、核心命令以及 pass / fail / skip 结果。该结果目录禁止被建模为正式质量真相或 release gate record。

#### 场景:远端编译失败后回看本地结果
- **当** 某次 Linux 或 Windows preflight 因编译或链接错误失败
- **那么** 系统必须在本地结果目录中保留足以定位问题的摘要与关键日志，而不是只在终端中短暂输出后丢失上下文

#### 场景:本地结果不被误认为正式 gate record
- **当** 开发者查看本地 preflight 输出目录
- **那么** 结果内容必须明确表现为开发者辅助记录，而不是与正式 CI / contract matrix 的门控记录混为同一真相源

### 需求:项目必须在 `docs/testing` 下提供本地跨平台 preflight 说明
项目必须在 `docs/testing` 下提供独立的本地 cross-platform preflight 说明文档，明确该能力的用途、远端宿主前置条件、配置模板位置、默认运行模式、Windows PowerShell 默认语义以及结果目录说明。该文档必须把本地 preflight 说明为开发者推荐工具，而不是正式 gate。

#### 场景:`docs/testing` 中可发现本地 preflight 说明
- **当** 贡献者查阅仓库中的 testing 文档以寻找跨平台本地验证方式
- **那么** 其必须能够在 `docs/testing` 目录下找到专门的本地 preflight 说明，而不是只能从零散注释或脚本源码中自行推断

#### 场景:文档明确区分本地 preflight 与正式 gate
- **当** 贡献者阅读本地 preflight 说明文档
- **那么** 文档必须明确说明该能力是推荐但不强制的研发预检工具，并与正式 GitHub Actions gate、contract matrix、`bridgingio-core --self-test` 保持边界区分
